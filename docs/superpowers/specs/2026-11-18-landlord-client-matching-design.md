# Подбор пар «собственник ↔ клиент» — дизайн

Дата: 18.11.2026. Ветка: `feat/landlord-preferences` (первый шаг — предпочтения собственника — уже в ней).

## Зачем

Менеджер берёт квартиру собственника в работу и записывает, кому тот готов сдать. Отдельно он заводит
клиентов, которые ищут квартиру, и записывает, что они ищут. Сейчас свести одно с другим можно только
по памяти. Нужно, чтобы система сама подсказывала пары:

- на карточке объекта в работе — **«Вероятные клиенты»**;
- на карточке клиента — **«Вероятные предложения»** (наши объекты в работе).

Подбор работает сам: без кнопки «подобрать», без настройки.

## Цели, не-цели, анти-цели

**Цели**
- Оба списка видны сразу при открытии карточки и отсортированы по проценту совпадения.
- Рядом с каждой парой написано, что не сходится («цена +$50», «животные»), чтобы менеджер решал сам.
- Расчёт — одним SQL-запросом в Postgres, без обращений к API Real Estate в момент показа.

**Не-цели (сейчас)**
- Уведомления «появился подходящий клиент», отметки «предлагали» / «отказался» — позже, отдельной
  таблицей поверх тех же правил (подход Б ниже).
- Подбор по всему рынку (все объявления Real Estate), а не только по нашим объектам в работе.
- Продажа. Только аренда: `listing_pins.direction = rent`.

**Анти-цели**
- Пара исчезла из-за одного несовпадения — так быть не должно: **жёстких условий нет**, показываем всех
  кандидатов по убыванию процента (решение пользователя).
- Неизвестное считается несовпадением — нельзя: незаполненный у одной из сторон критерий не штрафует
  и не учитывается в знаменателе процента.
- Комментарий собственника утекает агентам других компаний — нельзя (см. «Права»).

## Подходы

| | как | плюсы | минусы |
|---|---|---|---|
| **А. SQL при открытии** ✅ | признаки совпадения и процент считает один запрос, `ORDER BY score DESC LIMIT 10` | всегда свежо, нет новых таблиц и джоб, миллисекунды на тысячах строк | «новый подходящий клиент» сам не придёт |
| Б. Таблица пар | `matches(pin_id, client_id, score, reasons)`, пересчёт джобой при изменении любой стороны | мгновенное чтение, база для уведомлений и статусов «предлагали» | инвалидация, устаревание между пересчётами, вдвое больше кода |
| В. Расчёт в PHP | загрузить всех ищущих клиентов и посчитать в коде | проще всего | не то, что просили («оптимизированно для базы»); медленнее А при росте |

Выбран **А** (решение пользователя). Б добавляется позже без переделки: тот же SQL станет источником
для таблицы.

## Данные

### 1. Снимок квартиры на `listing_pins`

Подбору нужны цена, микрорайон и комнаты квартиры, а они живут в API. Копируем их к себе:

| колонка | тип | откуда (`App\RealEstate\Listing`) |
|---|---|---|
| `price_usd` | `numeric(12,2) null` | `priceUsd` |
| `rooms` | `smallint null` | `rooms` |
| `subdistrict_id` | `integer null` | `subdistrict.id` из ответа API (сейчас DTO его не берёт — добавить `subdistrictId`) |
| `title` | `string null` | `title` — для строки списка у клиента |
| `snapshot_at` | `timestampTz null` | когда обновлено |

- Заполняется в `Pins::take()` (там уже есть `Listing`).
- Обновляется при открытии карточки объекта (`ListingView` уже получает `Listing`): если поля
  изменились — `update`, иначе ничего (без записи на каждый просмотр).
- И раз в сутки — той же командой `pins:snapshot --stale=24h` в планировщике *(моё решение)*: иначе
  цена, сменённая на площадке, жила бы в подборе, пока карточку никто не откроет. Активных `rent`-пинов
  десятки, это десятки запросов к API в сутки.
- Для уже взятых объектов — artisan-команда `pins:snapshot` (проходит активные `rent`-пины, по одному
  `GET /listings/{id}`, с паузой под rate limit). Запускается один раз после деплоя.

### 2. Предпочтения собственника — `listing_pins.preferences` (jsonb, уже есть)

`occupants` (список), `people` (не больше), `home` (список), `note`.
**Цена, район и комнаты из окна собственника убираются**: они берутся из снимка объявления
(`ClientForm::profileFields` получает флаг `landlord`, который прячет `subdistrict_ids`, `rooms`,
`price_min`, `price_max`). Уже сохранённые в этих ключах значения игнорируются.

Смысл `home` у собственника: что в квартире есть и что он допускает. `pets` = «можно с животными»,
`furnished` = «с мебелью» и т. д.

### 3. Профиль клиента — `clients.profile` (jsonb, есть)

`rooms` из строки становится двумя числами `rooms_min`, `rooms_max` (форма — два числовых поля, как цена).
Данных для переноса нет (на 18.11 ни у одного клиента `rooms` не заполнено); миграция всё равно
переносит строку вида `2`, `2-3`, `2–3` в числа, остальное — в `note`.

## Правила совпадения

Кандидаты:
- для объекта: клиенты с `housing = looking` и `deleted_at IS NULL` — **всегда**, даже владельцу с
  включённым показом архива (`Archive::scope` в подборе не используется: архивный клиент не кандидат);
- для клиента: активные `listing_pins` с `direction = rent`, не удалённые.

Каждый критерий даёт вес, если **обе стороны** его заполнили; процент = набранное / сумма весов
заполненных критериев × 100. Если общих заполненных критериев нет — пара показывается внизу без процента
(«мало данных»).

| критерий | вес | совпало полностью | частично | не сходится → текст |
|---|---|---|---|---|
| Район | 30 | `pin.subdistrict_id` ∈ `profile.subdistrict_ids` | — | «другой район» |
| Цена | 25 | `price_min ≤ price_usd ≤ price_max` (пустая граница — открыта) | в пределах ±10% от границы — половина веса | «цена +$N» / «цена −$N» |
| Кто будет жить | 20 | `profile.occupants` ∈ `preferences.occupants` | — | «собственник против: <кто>» |
| Животные | 10 | клиент не просит `pets`, или собственник допускает `pets` | — | «животные» |
| Комнаты | 10 | `rooms_min ≤ pin.rooms ≤ rooms_max` | на 1 комнату мимо — половина | «комнат N» |
| Дом | 5 | доля пунктов `profile.home` (без `pets`), которые есть в `preferences.home` | пропорционально | «нет: <что>» |
| Людей | 5 | `profile.people ≤ preferences.people` | — | «людей больше, чем допускает собственник» |

Особые случаи:
- Клиент просит `pets`, а собственник `home` не заполнил — «Животные» не учитываются (неизвестно).
  Собственник заполнил `home`, но без `pets` — значит, против.
- Пустой список у собственника (`occupants`, `home`) или пустое `people` — «не ограничил / не знаем»:
  критерий не учитывается, а не «подходит всё». Эффект одинаковый — пара не штрафуется.
- **«Дом» — противоположные пары** *(моё решение)*: `furnished` ↔ `unfurnished`, `new_build` ↔
  `old_building`, `renovated` ↔ `no_renovation` ↔ `old_renovation`. Если клиент отметил пункт, а
  собственник — противоположный, это несовпадение («без мебели»). Если собственник не отметил ни пункт,
  ни противоположный — этот пункт не учитывается. `in_block` сравнивается только наличием.
- **Комнаты клиента:** `3+` → `rooms_min = 3`, `rooms_max` пусто; `студия` → `rooms_min = rooms_max = 1`
  *(моё решение)*; остальное — в `note`.

**Мало данных** *(моё решение)*: пара, у которой сумма весов известных критериев меньше 40 (из 105),
идёт ниже всех пар с достаточными данными и подписана «мало данных» вместе с процентом. Иначе
«1 из 1 = 100%» обгонял бы «5 из 6 = 92%». Сортировка: `enough_data DESC, score DESC, давность`.

### SQL

Один класс `App\Crm\Matching` с двумя методами: `clientsFor(ListingPin $pin, int $limit = 10)` и
`pinsFor(Client $client, int $limit = 10)`. Оба строят один и тот же запрос `clients × listing_pins`
(с фиксированной одной стороной). Каждый критерий — пара выражений в `SELECT`: `known_<k>` (обе стороны
заполнены, 0/1) и `hit_<k>` (0…1). Процент — `SUM(вес × hit) / NULLIF(SUM(вес × known), 0)` прямо в
запросе, `ORDER BY score DESC NULLS LAST, <давность> LIMIT :limit`.

jsonb-операторы: `profile->'subdistrict_ids' @> to_jsonb(pin.subdistrict_id)`,
`preferences->'occupants' ? (profile->>'occupants')`, `(profile->>'price_max')::numeric`.

Числа в jsonb: `ClientProfile::clean` уже приводит `price_*`, `people` к `int`, `subdistrict_ids` — к
списку `int`. В SQL всё равно приводить только при `jsonb_typeof(...) = 'number'`, иначе считать
неизвестным: битая строка не должна ронять запрос на всю карточку.

PHP превращает признаки строки в текст «что не сходится» — сам ничего не пересчитывает, поэтому правило
живёт в одном месте (SQL). Веса — константы класса.

### Индексы

Процент нельзя проиндексировать: при «показывать всех» запрос оценивает каждого кандидата. Это O(N)
по ищущим клиентам или по активным `rent`-пинам; на тысячах строк — миллисекунды. Индексы сужают
кандидатов:
- `clients`: частичный `(id) WHERE housing = 'looking' AND deleted_at IS NULL`;
- `listing_pins`: частичный `(id) WHERE status = 'active' AND direction = 'rent' AND deleted_at IS NULL`.

GIN по jsonb не нужен: фильтра по содержимому нет, есть только расчёт.

## Экраны

**Карточка объекта (`ListingView`)** — секция «Вероятные клиенты» под плашкой «Объект в работе».
Видна тем, кто вправе управлять объектом (`Pins::canManage`), и только на `rent`-объекте. До 10 строк:

```
Вероятные клиенты
 92%  Нино Беридзе  +995 5xx xxx xxx         →  карточка клиента
 70%  Гиорги М.     цена +$50 · животные
 —    Лаша К.       мало данных
```

**Карточка клиента (`ViewClient`)** — секция «Вероятные предложения» при `housing = looking`. До 10 строк:

```
Вероятные предложения
 88%  2 комн., Ваке · $600 · в работе у Нино        →  карточка объекта
 61%  3 комн., Сабуртало · $700 · цена +$100
```

Имя держателя показывается по тем же правилам, что в плашке «В работе у …» (`ListingView::banner`):
свои и видимые по ступени — по имени, остальные — «у другого агента группы». Предпочтения и комментарий
собственника на карточке клиента не показываются, только процент и текст несовпадений.

## Права

- «Вероятные клиенты» — `Pins::canManage($pin, $viewer)`. База клиентов общая на всю группу компаний
  (`Client::scopeVisibleTo` различает только архив — проверено по коду), поэтому дополнительных
  ограничений по компании нет; архив исключается всегда (см. «Кандидаты»).
- «Вероятные предложения» — все активные `rent`-пины группы, доступные по направлению смотрящего
  (`OrgAccess::directions`). Имя держателя — по правилам плашки.
- Комментарий собственника (`note`) никуда, кроме его объекта, не выводится.

## Что решено, а что оставлено исполнителю

Решено пользователем: показывать всех кандидатов по %; подход А; только аренда; предпочтения
собственника — тот же список, что у клиента, на объекте в работе.

Решено мной (можно оспорить): веса и пороги в таблице правил; ±10% по цене; противоположные пары в
«Доме»; порог «мало данных» 40; ежедневное обновление снимка; разбор `3+`/`студия`; «кто будет жить» у
собственника — несколько вариантов; цена/район/комнаты собственника — из объявления, а не из окна;
комнаты клиента — `rooms_min`/`rooms_max`; лимит 10 строк; снимок обновляется при открытии карточки.

Оставлено исполнителю: точная вёрстка секций в духе существующих (`x-filament::section`), формулировки
текстов несовпадений на en/ka, порядок равных процентов (предлагаю — свежие сначала), обработка
`pins:snapshot` при 404/недоступном объявлении (пропустить и вывести в отчёт команды).

## Тесты

- `Matching`: по одному тесту на критерий (совпало / частично / не сходится / неизвестно не штрафует),
  процент при пустых критериях, сортировка, лимит, архивные и `renting`-клиенты не попадают, закрытые и
  `sale`-пины не попадают.
- `ListingView`: секция видна держателю и скрыта чужому агенту; на `sale`-объекте её нет.
- `ViewClient`: секция с процентом и текстом; имя держателя скрыто для неопознаваемой компании;
  комментарий собственника не выводится.
- Снимок: `take()` заполняет поля; открытие карточки обновляет изменившуюся цену и не пишет без изменений.
- `pins:snapshot`: заполняет пустые, пропускает 404.
