# CRM-альфа: клиенты, объекты в работе, сделки, показы, задачи, журнал

Дата: 2026-10-25. Источник требований — `docs/GSHome/10_Модули_системы.md` (черновик владельца
проекта, разобран 25.10). Этот документ — что строим в альфе и где границы.

## Зачем

Владелец проекта идёт к руководителю агентства с ноутбуком: открывает админку и на готовых
данных проигрывает ситуации. Каждая ситуация — открытый вопрос из черновика, который
руководителю иначе не объяснить («звонит клиент, номер записан на другого — что делать?»).
Ответы руководителя потом поменяют модель: миграции и переделки ожидаемы и приняты заранее.

**Успех** — на показе можно руками пройти путь: взять объект в работу → найти или завести
клиента по телефону → открыть сделку → назначить показ → показ виден в задачах и под
колокольчиком → внести итог → увидеть это в ленте, журнале и отчёте руководителя. И
заготовленные демо-данные показывают сценарии из раздела «Демо-данные».

**Провал, даже если всё работает:** путь нельзя пройти за пару минут без подготовки;
демо-данные не показывают спорные ситуации; права дырявые — агент может менять чужие сделки,
видит чужие списки сделок или журнал. (Историю клиента со всеми сделками агент видит — это
решение владельца проекта, см. «Клиент».)

## Не делаем в альфе

- Telegram (бот, каналы, личные сообщения) — лента только в админке.
- Работу с собственником: договор, эксклюзив, комиссия продавца, вторая воронка.
- Копию карточки объявления при закреплении и её сверку с Real Estate.
- Автоматическое «объект недоступен» по исчезновению из API — только ручное действие.
- Редактирование клиента (кроме переноса номера, см. ниже).
- Двух агентов на одном объекте; сделку не-держателя на чужом объекте.
- Дизайн: стандартный Filament, отчёт — таблица без графиков.

## Что уже есть и на что опираемся

- Роли `owner`, `company_owner`, `team_lead`, `agent` (`App\Enums\Role`). Ступени прав из
  черновика ровно совпадают с `OrgAccess::visibleUsers()`: владелец — все, владелец компании —
  своя компания, тимлид — он сам и его агенты, агент — он сам. **Все новые проверки «кто что
  видит и с кем может действовать» — через `OrgAccess`**, ресурсы и политики своих правил
  не придумывают (`05_Оргструктура.md`).
- Направления — `OrgAccess::directions()`.
- Объявления живут в Real Estate, читаются через `App\RealEstate\RealEstateClient`. У
  объявления есть `cluster.id` (группа дублей, может быть `null`) и `is_primary`.
- Телефоны нормализуются `App\Support\PhoneNumber` (GE, E.164).
- Языки интерфейса ru / en / ka, подписи в `lang/{locale}/gshome.php`.
- Удаления людей нет; статусы людей — активен / заблокирован / в архиве.

## Сущности

### Клиент

- Телефон мобильный (E.164, уникален среди клиентов), имя, фамилия (необязательна).
- Пометки — несколько из четырёх: покупатель, арендатор, продавец, сдающий аренду.
  *Моё решение:* в альфе можно отметить несколько (вопрос открыт в черновике).
  «Продавец» и «сдающий аренду» — только метка, сделок для них нет.
- Надёжность — одно значение из списка в конфиге. *Моё решение:* «не проверен» (по умолчанию),
  «благонадёжный», «неблагонадёжный».
- Кто завёл. База общая на всю группу — *моё решение* для альфы, вопрос открыт.
- Карточка клиента показывает историю: все его сделки и показы — объект, агент, этап, итог,
  заметки показов. **Видят все роли, включая агента, — в том числе чужие сделки** (решение
  владельца проекта 25.10). Только чтение: открыть чужую сделку на изменение нельзя. Поиск
  по телефону находит клиента из любой компании группы.

**Поиск и заведение — по телефону.** Агент вводит номер:

- номера нет — заводит клиента;
- номер есть, имя совпало (с фамилией или без, без учёта регистра и лишних пробелов) —
  открывается существующий клиент;
- номер есть, имя другое — система не склеивает и не заводит второго молча, а спрашивает
  агента: «это тот же человек» (открыть существующего) или «это новый человек на этом
  номере». Во втором случае номер переходит к новому клиенту, у старого номер снимается,
  история остаётся у старого. Выбор пишется в журнал.

Редактировать клиента в альфе нельзя. Перенос номера — единственное изменение.

### Объект в работе (закрепление)

- Агент на карточке объявления нажимает «Взять в работу».
- Ключ закрепления — группа дублей: `cluster.id`, если он есть, иначе id объявления.
  Сохраняем оба: id объявления, с которого взяли, и id группы. В один момент у ключа не
  больше одного активного закрепления — это гарантирует база, не только код.
- Закреплённая группа на карточке любого объявления этой группы показывает «В работе у …»
  (имя — по правилам видимости `OrgAccess`, иначе «в работе у другого агента группы») и
  не даёт взять второй раз.
- «Мои объекты» — список закреплений агента. Карточки читаются живыми из API; если
  объявление недоступно — строка с id и пометкой «объявление недоступно», без падения.
- Передать: держатель или руководитель по ступени (`visibleUsers`). Получатель — человек,
  которого передающий видит, и у которого направление объекта есть в `directions()`.
- «Объект недоступен» (ручное действие держателя или руководителя): закрепление закрывается,
  все открытые сделки по нему закрываются с причиной «объект недоступен». В отчёте такие
  сделки — не неудача агента.
- «Снять с себя» — закрепление закрывается, открытых сделок быть не должно (или они
  закрываются тем же «объект недоступен» — *на усмотрение строителя, записать выбор*).

### Сделка

- Клиент × объект в работе. На одном объекте — несколько сделок, по одной на клиента.
  Открывает держатель объекта (и руководители по ступени).
- Этап — из настраиваемого списка. Каждая смена этапа пишется с датой: из неё считается
  время на этапе.
- Конец: «состоялась» (с суммой заработка и валютой) или «не состоялась» (с причиной —
  свободный текст), или «объект недоступен» (системная причина).
- Сделки агента видит он сам и руководители по ступени.

**Этапы.** Список хранится одной записью настроек (JSON). Экран настроек — только у владельца.
Каждый этап: неизменный ключ, подписи ru / en / ka, порядок, «скрыт», тип (обычный /
успех / неудача). Удаления нет — только «скрыт»: у старых сделок этап должен остаться
читаемым. Начальный набор: созвон с клиентом, показ назначен, показ прошёл, переговоры,
состоялась (успех), не состоялась (неудача).

### Показ

- Внутри сделки: дата и время (обязательны), заметки. Клиент и объект — из сделки.
- Несколько показов в сделке. Перенос — смена времени, событие в ленте и журнале.
- Итог — один из пяти ТЗ (фиксированный список в коде): сделка подтверждена, сделка не
  состоялась, нужен повторный контакт, клиент недоступен, переговоры продолжаются. Итог
  показа и этап сделки — **два поля**; агент двигает этап сам.
- Напоминания (колокольчик): *моё решение по времени* — за 2 часа до показа; в день показа
  в 09:00; через 1 час после времени показа, если итог не внесён, и дальше раз в день до
  внесения.

### Задача

- Текст, исполнитель, автор, срок (необязателен), статус из конфига: открыта, выполнена,
  отменена.
- Кто кому: агент — себе; тимлид, владелец компании, владелец — себе и тем, кого видят
  (`visibleUsers`). Задачи агента видят он и руководители по ступени.
- Новая задача другому человеку → уведомление под колокольчиком исполнителю.
- **Показ — тоже задача.** Экран «Мои задачи» показывает в одном списке задачи и
  предстоящие показы без итога. Показ не копируется в задачи: строка ведёт в показ, и
  закрывается он внесением итога, а не кнопкой «выполнена».

### Жизненный цикл и решения по краям (мои решения, 25.10)

- **Кто берёт в работу:** любая роль, только объявление своего направления (`directions()`).
- **Передача объекта:** открытые сделки и их показы переходят к новому держателю (сделка
  принадлежит закреплению). Напоминания идут новому держателю. В журнале — кто, кому, когда.
- **Сделка «состоялась»** закрывает закрепление: объект продан или сдан. Остальные открытые
  сделки по нему закрываются причиной «объект недоступен» и в неудачи не идут.
- **«Снять с себя» и «В архив»** для закрепления и клиента — только без открытых сделок.
  Сначала закрыть сделки.
- **Ключ закрепления фиксируется при взятии.** Если Real Estate потом перестроит группы и
  у объявления окажется другой `cluster.id`, закрепление остаётся по старому ключу;
  карточка ищет закрепление и по id объявления, и по текущему `cluster.id`. Два
  закрепления на одну квартиру после перестройки — терпим, помечаем на карточке.
- **Перенос номера:** телефон клиента может быть пустым (уникален среди непустых). Сделки
  и показы старого клиента остаются у него. Вернуть номер в альфе нельзя. Выбор делает
  любой, кто заводит клиента.
- **Напоминания** получает держатель сделки (её агент). Время — Asia/Tbilisi. Нужен
  планировщик: локально профиль `scheduler`, на проде — crontab (уже есть).
- **Заработок:** вносит тот, кто закрывает сделку как «состоялась». Валюта — USD или GEL
  (список в конфиге). После закрытия в альфе не правится.
- **«Показывать архивное»** — личная настройка владельца.
- **Лента:** агент, тимлид, владелец компании — события своей компании; владелец — все.
  **Журнал** — по человеку, который действовал (`causer`), в пределах `visibleUsers`,
  включая «открыл карточку».

## Сквозное

### Ничего не удаляется

Везде вместо «Удалить» — «В архив». Архивное пропадает с экранов. У владельца в настройках
переключатель «Показывать архивное»: включён — архивные клиенты, закрепления, сделки,
показы, задачи видны рядом с обычными (с пометкой). Исключение — «Сохранённые объявления»:
остаются как есть (решение 14.10), это записать в `02_Решения.md`.

### Журнал действий

Пакет `spatie/laravel-activitylog`, как в BigMed. Пишется каждое действие человека:
создал / изменил (было → стало) / в архив / из архива для всех новых сущностей; взял в
работу, передал, «объект недоступен», сменил этап, назначил / перенёс показ, внёс итог,
выбор при конфликте номера; **открыл карточку объявления** (кто, когда, какое объявление).
Журнал не правится и не архивируется.

Экран журнала — у тимлида (по своим агентам), владельца компании (по компании),
владельца (по всем); у агента нет. Фильтры: человек, тип действия, период, объявление
(чтобы ответить на «кто смотрел это объявление и сколько раз»). На карточках клиента,
сделки, закрепления — вкладка с журналом этой записи для тех же ролей.

### Лента

Короткая выдержка из журнала — события работы (взял в работу, открыл сделку, назначил /
перенёс показ, сменил этап, итог, закрыл сделку). Без имени и телефона клиента. Видна всем
ролям на главной: агент, тимлид, владелец компании — события своей компании, владелец —
всех. Это то, что потом уйдёт в Telegram.

### Колокольчик

Встроенные уведомления Filament в базе. Непрочитанные — значок мигает, пока человек не
отметит прочитанным. Источники: новая задача, три напоминания о показе.

### Отчёт

Одна таблица, строка на агента: объектов в работе; сделок открыто; показов проведено;
сделок состоялось / не состоялось (без «объект недоступен»); заработок (сумма закрытых,
по валютам); среднее время на каждом этапе; **зависших объектов** — закрепление без
движения больше 7 дней (движение — новая сделка, показ, смена этапа, итог). Зависшие
выделены красным, по клику — список. Период — фильтр. Строки — по `visibleUsers`: агент
видит только себя.

## Демо-данные

**Показ — на проде** (`gshome.devstudio.ge`, решение владельца проекта 25.10). Там уже
демо-люди из локальной базы. Сидер запускается на сервере после деплоя — это делается
отдельным шагом с подтверждением, не автоматически при деплое.

Отдельный сидер поверх людей, которые уже есть в базе (на проде — перенесённые из
`OrgDemoSeeder`). Безопасен для повторного запуска: свои записи узнаёт и пересоздаёт, чужие
не трогает.
Берёт **настоящие id объявлений** из API Real Estate на момент запуска (иначе карточки не
откроются), предпочитая объявления с группой дублей. Сценарии:

1. **Конфликт номера:** клиент «Нино Беридзе» с номером X; на показе вводим номер X с
   именем «Леван Капанадзе» — система спрашивает.
2. **Нино и Гиорги:** объект закреплён за агентом Нино; Гиорги открывает тот же объект
   (или его дубль) — видит «В работе у Нино», взять не может. Это и есть вопрос руководителю.
3. **Зависший объект:** закрепление, по которому последнее движение 8 дней назад — красное
   в отчёте.
4. **Группа дублей:** закрепление по одной копии — вторая копия той же группы тоже «в работе».
5. **Итог не внесён:** вчерашний показ без итога — висит в задачах и под колокольчиком.
6. **Журнал «приходил ли агент»:** у сделки история: задача «перезвонить» поставлена и
   закрыта, показ назначен, перенесён, итог внесён — видно по журналу с датами.
7. Несколько закрытых сделок (успех с суммой, неудача, «объект недоступен»), чтобы отчёт
   не был пустым.

Даты в прошлом пишутся и в записи, и в журнал (журнал должен показать «8 дней назад»).
